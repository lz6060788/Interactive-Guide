# 画面比例与图片填充模式渲染逻辑

> 2026-05-21

## 一、知识包画面比例（Resolution）

### 1.1 定义

知识包级别的属性 `resolution` 控制整个导览的画面比例，可选值：

| 值 | 含义 | 基础像素 |
|---|---|---|
| `'16:9'` | 横屏 | 1920 × 1080 |
| `'9:16'` | 竖屏 | 1080 × 1920 |
| `'375*808'` | iPhone 常规竖屏 | 375 × 808 |

类型定义（`src/shared/types.ts`）：

```typescript
export type PackageResolution = '16:9' | '9:16' | '375*808'
```

### 1.2 数据流

```
KnowledgePackage.resolution ('16:9' | '9:16' | '375*808')
  → buildWorkspaceManifest / buildManifest → PublishManifest.resolution
  → 渲染引擎读取 → 计算容器尺寸
```

resolution 存储在 `guide.json` 的 `KnowledgePackage` 和发布后的 `manifest.json` 的 `PublishManifest` 中，是**知识包级别**属性，影响所有节点。

### 1.3 用途

1. **图片生成**：调用生图 API 时传入对应的基础像素尺寸
2. **容器尺寸计算**：渲染引擎根据比例计算显示区域的宽高
3. **视觉模型提示词**：构建构图提示词时传入画布尺寸

## 二、节点图片填充模式（ImageFitMode）

### 2.1 定义

节点级别的属性 `imageFitMode` 控制单个节点图片在容器内的填充方式：

| 值 | 含义 |
|---|---|
| `'fill'`（默认） | 拉伸填满容器，可能变形 |
| `'fitHeight'` | 高度撑满容器，宽度等比缩放（可拖动） |
| `'fitWidth'` | 宽度撑满容器，高度等比缩放（可拖动） |

类型定义（`src/shared/types.ts`）：

```typescript
export type ImageFitMode = 'fill' | 'fitHeight' | 'fitWidth'
```

### 2.2 应用场景

- **fill**：图片经过 AI 生成，尺寸与容器比例一致时使用（默认）
- **fitHeight / fitWidth**：用户上传的图片、或 AI 生成的图片比例与容器不一致时使用

### 2.3 数据流

```
KnowledgeNode.imageFitMode → PublishNode.imageFitMode（manifest.json）
  → 渲染引擎读取 → 选择对应的 CSS 渲染策略
```

## 三、渲染引擎 DOM 布局

### 3.1 整体结构

```
Modal（黑色弹窗）
├── 宽高：min(90vw, 90vh × ar) × min(90vh, 90vw / ar)
├── display: flex; flex-direction: column; overflow: hidden
│
└── Player Area（flex: 1; display: flex; align-items: center; justify-content: center）
    │
    └── Container（w: 100%; h: 100%; aspect-ratio: 9/16; overflow: hidden）
        │
        ├── [fill 模式] img（w: 100%; h: 100%; object-fit: fill）
        │
        ├── [fitHeight 模式] Wrapper（position: absolute; inset: 0; display: flex; align-items: center）
        │   └── img（height: 100%; flex-shrink: 0）
        │
        ├── [fitWidth 模式] Wrapper（position: absolute; inset: 0; display: flex; align-items: center）
        │   └── img（width: 100%; flex-shrink: 0）
        │
        └── Hotspot Overlay（position: absolute; 基于 imgRect 定位）
```

### 3.2 容器尺寸计算

Modal 的宽高由共享分辨率表换算得到，确保不超出视口：

```typescript
const { width, height } = getResolutionDimensions(resolution)
const ar = width / height
const aspectRatioCss = `${width} / ${height}`

const maxWVw = 90   // 最大宽度占视口宽度的 90%
const maxHVh = 90   // 最大高度占视口高度的 90%

const modalW = `min(${maxWVw}vw, ${maxHVh}vh * ${ar})`
const modalH = `min(${maxHVh}vh, ${maxWVw}vw / ${ar})`
```

**示例（375*808 iPhone 竖屏）：**
- `ar = 375 / 808 ≈ 0.464`
- `aspectRatioCss = '375 / 808'`
- `modalW = min(90vw, 90vh × 0.464...)`
- `modalH = min(90vh, 90vw / 0.464...)`

**示例（9:16 竖屏）：**
- `modalW = min(90vw, 90vh × 0.5625) = min(90vw, 50.625vh)` → 取较小值
- `modalH = min(90vh, 90vw / 0.5625) = min(90vh, 160vw)` → 取较小值

### 3.3 三种填充模式的 CSS 策略

#### fill 模式

```
img { width: 100%; height: 100%; object-fit: fill; }
```

- 图片被拉伸至与容器完全一致
- 如果图片比例与容器比例不同，图片会变形
- 适合 AI 生成的与容器比例一致的图片

#### fitHeight 模式

```
Wrapper { position: absolute; inset: 0; display: flex; align-items: center; }
img { height: 100%; flex-shrink: 0; }
```

- 浏览器根据 `height: 100%` 和图片原始比例自动计算宽度
- 例：容器 1080×1920，图片 4096×2737（比例 ~1.5:1）
  - 图片高度 = 1920px
  - 图片宽度 = 1920 × (4096/2737) ≈ 2871px
  - 超出容器宽度 1080px → 两侧溢出，overflow:hidden 裁剪
- `flex-shrink: 0` 防止 flex 容器压缩图片宽度
- `align-items: center` 默认水平居中
- 拖动通过 `translateX` 移动 wrapper 实现

#### fitWidth 模式

```
Wrapper { position: absolute; inset: 0; display: flex; align-items: center; }
img { width: 100%; flex-shrink: 0; }
```

- 与 fitHeight 对称，宽度撑满容器，高度等比溢出

### 3.4 拖动逻辑

fitHeight/fitWidth 模式下，图片通过 wrapper 的 `transform: translateX()` 实现拖动：

```
拖动距离 = translateX + (鼠标当前位置 - 鼠标起始位置)
拖动边界 = ±(图片宽度 - 容器宽度) / 2
```

### 3.5 Hotspot 定位

Hotspot 使用归一化坐标 `(normalizedX, normalizedY)`，叠加在图片可视区域上方：

```
Hotspot Overlay:
  left = imgRect.x（图片可视区域相对于容器的偏移）
  top  = imgRect.y
  width = imgRect.w
  height = imgRect.h

hotspot 按钮:
  left = normalizedX × 100%
  top  = normalizedY × 100%
```

`imgRect` 通过 `wrapper.getBoundingClientRect()` 计算，反映图片的可视区域。

## 四、当前问题

### 4.1 问题描述

设置了 `imageFitMode: 'fitHeight'` 的根节点（商业航天产业链），在预览时图片宽度被压缩。

- 图片原始尺寸：4096 × 2737（比例 ~1.5:1，横屏图）
- 容器比例：9:16（竖屏）
- 预期：图片高度撑满容器，宽度等比放大（约 2871px），两侧溢出可拖动
- 实际：图片宽度被压缩到与容器等宽（约 1080px），高度相应被压缩

### 4.2 调试数据

用户检查 img 标签的 computed style：

```
height: 100%; display: block; user-select: none; opacity: 1; flex-shrink: 0;
```

所有预期的 CSS 属性都已设置，但宽度仍然被压缩。

### 4.3 历史排查过程

| 阶段 | 方案 | 结果 |
|---|---|---|
| v1 | `object-fit: none` + `height: 100%; width: auto` | object-fit: none 显示自然像素，图片不缩放 |
| v2 | 去掉 object-fit，`height: 100%; width: auto` | 图片应该按比例缩放，但宽度仍被压缩 |
| v3 | 添加 flex wrapper 容器 + `flex-shrink: 0` | flex-shrink 已禁用，但宽度仍被压缩 |
| v4 | wrapper 使用 `translateX` 拖动 | 拖动逻辑正确，但图片本身已被压缩 |

### 4.4 根因分析（待确认）

可能的原因：

**假设 A：flex 容器的 intrinsic size 约束**

在 flex 容器中，子元素的 intrinsic size 受 `min-width: auto`（flex 默认值）约束。`min-width: auto` 对于有内容的 flex 子元素，其最小值等于内容的 min-content 宽度。对于 img 元素，min-content 宽度 = 图片自然宽度。这意味着 flex 子元素的宽度不应该被压缩到小于自然宽度。

但 `height: 100%` 改变了计算逻辑：浏览器需要在 100% 高度约束下计算宽度。如果 flex 算法优先处理 `height: 100%` 为「已确定尺寸」，然后按 intrinsic aspect ratio 计算宽度，结果应该正确。

**假设 B：Container 的 `w="100%" h="100%"` + `aspect-ratio` 的冲突**

Container 同时设置了 `w: 100%`、`h: 100%` 和 `aspect-ratio: 9/16`。当两者都明确设置时，`aspect-ratio` 不改变布局尺寸，仅用于计算 intrinsic size。这可能不影响子元素。

**假设 C：多层 flex 嵌套导致尺寸坍缩**

```
Modal (flex column)
  → Player Area (flex: 1, flex row, minH: 0)
    → 内层 Box (w:100%, h:100%, flex row, minH:0)
      → Container (w:100%, h:100%, position:relative)
        → Wrapper (position:absolute, inset:0, flex row)
          → img (height:100%, flex-shrink:0)
```

多层 flex 嵌套中，每一层的 `w: 100%` 实际计算值可能因 flex 算法的 intrinsic size 传递而不同。

## 六、下一步方向

### 6.1 排除 flex 干扰

放弃在 flex 容器内使用 `height: 100%` 的方案，改用纯 absolute positioning：

```css
/* Wrapper */
position: absolute; inset: 0; overflow: hidden;

/* img */
position: absolute;
height: 100%;
width: auto;
top: 50%;
transform: translateY(-50%);  /* 垂直居中 */
```

- 不依赖 flex，完全用 absolute + transform 实现布局
- 拖动通过修改 `translateX()` 实现（叠加在 translateY 上）
- 消除所有 flex shrink / grow / intrinsic size 干扰

## 七、本次修订结论（2026-05-21 补充）

本节记录本轮实际落地后的最终结论，用于覆盖前文中已经失效的“待确认”分析与旧方案描述。

### 7.1 fitHeight / fitWidth 的最终渲染模型

`fitHeight` / `fitWidth` 已统一改为图片自身 absolute 定位，而不是 wrapper + flex 布局：

```css
img {
  position: absolute;
  left: 50%;
  top: 50%;
  max-width: none;
  max-height: none;
}

/* fitHeight */
img {
  height: 100%;
  width: auto;
  transform: translate(-50%, -50%) translate(offsetX, 0);
}

/* fitWidth */
img {
  width: 100%;
  height: auto;
  transform: translate(-50%, -50%) translate(0, offsetY);
}
```

- 预览端与 runtime 都采用同一套语义
- `fitHeight` 只允许横向拖动，`fitWidth` 只允许纵向拖动
- hotspot 区域一律基于图片真实 `getBoundingClientRect()` 计算，而不是基于外层 wrapper

### 7.2 内置转场没有消失，根因在于 drag-fit 节点兼容层

本轮已经恢复 `fitHeight` / `fitWidth` 节点上的 builtin transition。最终做法不是继续整体禁用，而是：

1. 保留 builtin transition 的播放链路
2. 为 `pan` / `flip` / `zoom` 单独适配 drag-fit 节点的视觉层
3. 让转场层复用节点自己的 `imageFitMode` 语义，而不是退回普通 `fill` 图片

这意味着：

- `fill -> fill`
- `fill -> fitHeight`
- `fitHeight -> fitWidth`
- `fitWidth -> fill`

这些场景都可以继续走内置转场，而不是硬切换。

### 7.3 Zoom 新增四点区域缩放

`zoom` 转场配置已扩展为两种模式：

- `focusMode: 'center'`：保持原有中心点缩放
- `focusMode: 'quad'`：使用 `focusQuad` 指定目标区域

共享类型位于 `src/shared/types.ts`：

```typescript
export interface NormalizedPoint {
  x: number
  y: number
}

export interface ZoomFocusQuad {
  topLeft: NormalizedPoint
  topRight: NormalizedPoint
  bottomRight: NormalizedPoint
  bottomLeft: NormalizedPoint
}
```

`zoom` 编辑器、`EdgeModal`、共享校验器都已同步支持该结构。

### 7.4 四点区域缩放的最终约束

实际验证后确认：四点区域不能直接按自由矩形做 `scaleX / scaleY` 非等比缩放，否则会出现横向拉伸、镜头路径错误和落点失真。

当前约束如下：

1. 目标窗口必须与知识包画面比例保持一致
2. 四点配置主要以上边宽度为基准
3. 目标窗口高度由当前画幅比例自动反推
4. 运行时使用统一 `scale`，不再使用横纵独立缩放

这保证了镜头语义是“平移 + 等比缩放”，而不是对原图做自由拉伸。

### 7.5 Zoom 起始镜头的最终处理

本轮排查中最关键的结论是：转场起始帧不能重新解释当前图片的 `left: 50% + top: 50% + transform: translate(-50%, -50%) translate(...)` 布局公式，否则很容易回到中心区域或复用错误位置。

最终处理方式：

1. builtin transition 创建当前图视觉层时，直接读取当前 `nodeImage.getBoundingClientRect()`
2. 将当前图片在容器中的真实可视几何状态烘焙为固定的 `left / top / width / height`
3. 对当前图快照清空基础 `transform`，只保留像素几何结果
4. `zoom-renderer` 在拼接动画 transform 时会将 `'none'` 归一化为空值，避免生成无效 CSS transform

这样 builtin `zoom` 的起始帧就等于用户当前看到的那一帧，不会再先回中心后开始放大。

### 7.6 预览端与 PlayerCore 的 DOM 引用同步是必要条件

预览层的图片节点会随着 `currentNodeId` 和 `imageFitMode` 变化被重新挂载。如果 `PlayerCore` 只缓存初始化时的 `nodeImage` 引用，就会出现两类问题：

1. 首次进入节点时转场层拿到旧节点或空节点，表现为无动画或卡顿
2. 返回 root 后再次进入其他节点时，错误复用上一次节点的拖动状态

因此本轮补充了 `PlayerCore.updateRefs()`，在预览层切节点后将最新的：

- `container`
- `nodeImage`
- `video`
- `nodeIframe`

重新同步给运行时引擎，保证转场快照永远来自当前真实 DOM。

### 7.8 回归重点

后续若继续修改转场相关逻辑，建议至少回归以下场景：

1. `root -> 任意子节点` 首次进入 builtin `zoom`
2. `子节点 -> root -> 另一子节点` 连续进入 builtin `zoom`
3. `fitHeight` 下先横向拖动，再触发 `zoom`
4. `fitWidth` 下先纵向拖动，再触发 `zoom`
5. `focusMode: 'center'` 与 `focusMode: 'quad'` 两类配置
6. `pan` / `flip` / `zoom` 三种 builtin transition 与 drag-fit 节点的组合

1. 容器（containerRef）的实际 computed width/height
2. wrapper 的实际 computed width/height
3. img 元素的 computed width/height（而非 inline style）
4. 各层的 flex 属性是否被 Chakra UI 额外覆盖
