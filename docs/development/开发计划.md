## 3. 开发总原则

- 优先打通最小闭环，不同时铺开全部能力。
- 优先保证输入协议、构建产物和运行时契约三者一致。
- 管理端、构建端、运行时都围绕同一份 schema 和 manifest 工作。
- 每个阶段结束后，都要能产生明确可验证结果，而不是只完成局部代码堆积。
- 第一阶段优先本地文件系统驱动，不急于引入数据库、任务队列和复杂基础设施。

## 7. Phase 2：构建端最小闭环

### 7.1 目标

- 打通从 `package.json` 到 `publish/manifest.json` 的最小构建链路。
- 第一阶段允许热点推荐先为空壳，人工补齐。

### 7.2 任务

- 实现包读取与校验流程：
  - 读取 `data/packages/{packageId}/current/package.json`
  - 生成 `buildId`
  - 写入 `build.json`
  - 产出 `validation-report.json`
- 实现节点构建最小链路：
  - 节点页面编排输出
  - 节点图片生成或占位产物输出
- 实现热点中间文件输出：
  - `hotspots.recommended.json`
  - `hotspots.final.json`
- 实现边构建最小链路：
  - 边转场描述输出
  - 边视频生成或占位产物输出
- 实现发布收口：
  - 生成 `publish/manifest.json`
  - 拷贝节点图片与边视频到发布目录

### 7.3 完成标准

- 任意一份合法知识包都能生成一份可加载的发布包。
- `data/builds/{buildId}` 和 `data/publish/{packageId}/{version}` 目录结构正确。
- 即使图片或视频仍为占位资源，整个构建链路也已闭环。

## 8. Phase 3：运行时播放器最小闭环

### 8.1 目标

- 基于 `PublishManifest` 实现最小可运行播放器。
- 证明发布层契约能真正支撑用户端探索体验。

### 8.2 任务

- 实现 manifest 加载器
- 实现节点图片展示
- 实现热点白点渲染
- 实现热点点击切换
- 实现边视频存在时的转场播放
- 实现根节点启动逻辑
- 实现错误态和资源缺失保护

### 8.3 完成标准

- 播放器能从 `root` 启动。
- 可正常点击热点切换到目标节点。
- 有视频时先播视频，无视频时直接切换。
- 运行时不依赖构建中间文件。

### 11.2 任务

### 11.3 完成标准

- 资源复用开始显著降低构建耗时与成本。

- 节点图片缓存与边视频缓存已接入实际构建链路。
- 边视频生成前已接入首尾帧视觉规划，不再只依赖单层视频 prompt。
- 低连续性边仍需继续优化，但技术闭环已经建立。

## 12. 当前推荐开发顺序

### 12.1 严格顺序

1. `Phase 0 项目骨架初始化`
2. `Phase 1 类型与契约落地`
3. `Phase 2 构建端最小闭环`
4. `Phase 3 运行时播放器最小闭环`
5. `Phase 4 管理端最小闭环`
6. `Phase 5 构建后台增强`
7. `Phase 6 自动化增强`

### 12.2 为什么这样排

- 如果不先固定类型和契约，后续前后端会各自实现一套模型。
- 如果不先打通构建链路，管理端只能停留在编辑 UI，无法验证真实产物。
- 如果不先验证运行时播放器，管理端预览也无法站稳。
- 管理端应建立在已知可消费的构建产物和 manifest 之上，而不是反过来驱动底层契约漂移。

## 14. 当前阶段的首批开发任务

- 立即开始的任务应聚焦在 `Phase 0 + Phase 1`：
  - 初始化项目目录
  - 建立 TypeScript 基础配置
  - 创建共享类型目录
  - 写入 schema 类型
  - 写入 manifest 类型
  - 写入 build record 类型
  - 准备一份 demo package 数据

- 在这批任务完成之前，不建议直接开始：
  - 管理端界面开发
  - 复杂构建调度
  - 自动热点推荐

## 15. 风险与控制点

### 15.1 风险

- 前后端类型漂移
- 管理端提前实现过多 UI，脱离真实产物
- 构建层与发布层混杂
- 热点数据格式频繁变化
- 预览和正式发布使用两套不同数据结构

### 15.2 控制点

- 所有类型先落到共享层
- 预览弹窗直接复用发布契约
- 构建目录和发布目录严格分层
- 每阶段结束前做一次文档对齐

## 16. 文档维护规则

- 每完成一个阶段，就更新本文件中的：
  - 当前项目状态
  - 已完成阶段
  - 下一阶段任务
- 若开发顺序调整，优先修改本计划，再开始执行。
- 若设计文档有重大变更，应同步检查本计划是否需要改动。

## 17. 当前结论

- 当前项目已经完成从知识包编辑、节点出图、热点校准、边视频生成到预览播放的第一轮完整闭环。
- 构建后台增强已不再停留在设计阶段，而是具备可操作的单对象重跑与状态观测能力。
- 自动化增强已进入“局部可用、仍需提质”的阶段，尤其是：
  - 热点自动推荐
  - 边转场视觉规划
  - 节点图对象存储暴露
- 下一轮工作的重点不再是补齐是否有能力，而是提升已有能力在复杂边上的稳定性和一致性。
- 在此基础上，局部子图节点的运行时语义和编辑器生产方式需要进入下一轮架构升级，以降低 iframe 依赖并统一缩放进入后的稳定态规则。
- 与此同时，项目已确认需要新增一套独立于当前 runtime 的“独立全景 HTML 产物”，用于承载中游/下游的全景图、滚动激活三级列表、聚焦框高亮和遮罩连接线等体验；相关方案见 `docs/独立全景HTML产物方案设计.md`。
