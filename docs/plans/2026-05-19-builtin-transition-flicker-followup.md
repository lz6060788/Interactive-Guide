# 内置转场结束闪烁问题跟踪

## 1. 文档目的

- 记录当前“内置转场结束仍有闪烁”的现状。
- 归档本轮已做过的尝试、出现过的回归和已确认无效的方向。
- 为下一次新会话提供统一上下文，避免重复试错。

## 2. 当前结论

截至提交 `80a2e96`，当前运行时相关状态如下：

- `PlayerCore` 已从宿主层逻辑中抽离，预览与独立运行时共用同一套内核。
- 视频转场的“结束后闪回 A 再切到 B”问题已修复。
- 视频转场当前表现稳定，没有明显黑屏或结束闪烁。
- 资源预加载已独立为 `src/runtime/player-core/resource-preloader.ts`，并改为初始化阶段全量预热。
- 预加载期间宿主层使用 loading 覆盖层，不再卸载播放器主体 DOM。
- 剩余问题集中在：`builtin` 内置转场结束瞬间仍会出现一次轻微闪烁。

## 3. 问题定义

当前剩余问题不是整段黑屏，也不是旧节点 A 再次完整露出，而是：

- `pan / flip / zoom` 等内置转场播放结束后
- 目标节点 B 已准备切入稳定态
- 但在“冻结帧 -> 宿主真实主图”交接瞬间仍有一次轻微闪烁
- 视觉上更像下半张图或局部区域跳一下

这说明当前问题已经从“状态切换顺序错误”收敛为“最终接管层与真实主图提交之间仍有细微不一致”。

## 5. 已确认有效的修复

### 5.1 修复“原始 A 暴露”问题

有效结论：

- `PlayerCore` 不能把 `fromEl / toEl` 先直接插入转场容器，再由 renderer 重新克隆一遍。
- 转场期间，真正参与动画的 DOM 必须完全由 renderer 独占。

### 5.2 修复视频转场结束闪回 A

有效结论：

- `switchNode()` 不能在宿主完成切到 B 之前，提前恢复旧节点基础图。
- 运行时状态变更与宿主渲染提交必须保持同一步调。

### 5.3 宿主确认后再清理视觉层

有效结论：

- 视频层或内置转场冻结层不能在 `stateChange` 发出后立刻清理。
- 应由宿主在确认目标稳定态已经接住后，再通知 `PlayerCore` 清理。

### 5.4 预加载 loading 改为覆盖层

有效结论：

- 预加载期间不能条件卸载播放器主体 DOM。
- 否则 `PlayerCore` 会继续持有旧的 `container / nodeImage / video` 引用。
- 这会导致视频层和转场层被渲染到已经脱离页面的旧 DOM 上，直接表现为黑屏。

## 6. 已尝试但未彻底解决的问题方向

### 6.1 单纯提前显示下一节点真实主图

结论：

- 这个方向不稳，不适合作为最终方案。
- 原因是内置转场存在透明区、旋转区或边缘暴露区。
- 如果底层真实主图 B 过早显示，容易重演“原始底层泄露”类问题。

### 6.2 仅依赖预加载解决结束闪烁

结论：

- 预加载能减少资源未就绪导致的卡顿。
- 但当前剩余闪烁不是主资源未到位，而是最终接管层与真实主图的交接时序和视觉一致性问题。

### 6.3 仅通过 `img.complete` 判定宿主已完成接管

结论：

- 这个判定偏宽。
- 日志曾显示：
  - 宿主先确认
  - `PlayerCore` 立即清掉冻结帧
  - 随后真实主图才触发 `onLoad`
- 这会导致冻结帧撤掉略早于真实主图稳定接管。

## 7. 本轮尝试与结果

### 7.1 增加转场链路日志

目的：

- 定位闪烁到底发生在开始前、结束后，还是资源加载阶段。

结果：

- 已确认视频转场结束问题的主因是“先清可见层，后宿主提交”。
- 已确认内置转场剩余问题更偏向“冻结帧接管不够稳”。

### 7.2 引入宿主确认机制

目的：

- 让 `PlayerCore` 在收到宿主确认后再移除视频层或内置转场冻结层。

结果：

- 视频转场问题基本解决。
- 内置转场结束闪烁明显收敛，但未完全消失。

### 7.3 收紧 `builtin` 确认条件

目的：

- 不再在普通下一帧就确认，而是尽量等待真实主图 ready。

结果：

- 能减轻问题，但仍不能完全消除。
- 说明仅仅收紧确认时机还不够，还需要检查“冻结帧本身”与“真实主图稳定态”是否完全一致。

### 7.4 改造为全量预加载

目的：

- 在初始化阶段提前暖好所有节点图片与边视频，降低资源切换抖动。

结果：

- 预加载本身有效，视频体验更稳定。
- 但与内置转场结束闪烁不是同一层问题。

### 7.5 预加载 loading 首次实现引发黑屏回归

问题：

- 首次把 loading 做成条件渲染，导致播放器主体 DOM 被卸载。

结果：

- 视频与内置转场一度都退化为黑屏。

修复：

- 改成覆盖层，不再卸载 DOM。

## 8. 当前最可能的根因

当前最值得优先验证的方向是：

- `builtin` 动画结束后保留下来的“冻结帧”
- 与宿主真实主图 `img`
- 在以下任一维度上仍存在细微差异：
  - 尺寸
  - 裁切
  - `object-fit`
  - transform 清理时机
  - 最终透明度
  - 最后一帧 paint 提交顺序

因此当前剩余闪烁更像是：

- 不是“没有接住”
- 而是“接住了，但接管层和真实层不是完全同一张画面”

## 9. 下一会话建议排查顺序

建议下一次新会话按下面顺序推进：

1. 先只关注 `builtin`，不要再同时动视频转场。
2. 对比冻结帧元素与宿主真实主图的最终样式：
   - 容器尺寸
   - `width / height`
   - `object-fit`
   - `transform`
   - `transform-origin`
   - `opacity`
   - `border-radius`
3. 核查冻结帧是否来自“动画态最后一帧”，还是“重新构造的一张静态图”。
4. 如果是重新构造，优先改为“从最终可见层直接冻结当前视觉结果”。
5. 如果样式完全一致但仍闪：
   - 再验证是否需要在 `node-image:onLoad` 之后额外延一帧再清理冻结层。
6. 不要再尝试“直接提前显示底层真实 B 图”作为主方案。

## 10. 建议的最小实验

下一次会话建议优先做以下两个最小实验：

### 实验 A：冻结帧与真实主图样式对比

目标：

- 找出内置转场结束瞬间到底是哪一层发生了几何或样式差异。

建议做法：

- 在 `builtin` 结束后、宿主确认前，读取：
  - 冻结帧元素 `getBoundingClientRect()`
  - 宿主真实主图 `getBoundingClientRect()`
  - 两者关键 style
- 将差异直接打印为结构化对象

### 实验 B：冻结层延后一帧清理

目标：

- 判断当前残余闪烁是不是最后一帧 paint 竞争问题。

建议做法：

- 在 `builtin` 路径下，宿主确认后不要立即清理冻结层
- 改为再过一个 `requestAnimationFrame` 再清理

判定：

- 如果明显改善，说明问题仍然与最终 paint 交接顺序有关
- 如果几乎无改善，说明更应优先检查冻结帧和真实主图样式不一致

## 11. 暂不建议继续扩大的改动

在新会话开始前，不建议再同时推进以下方向：

- 节点渲染抽象 `NodeRenderer`
- 特殊边动作层 `EdgeAction`
- 大规模重写 renderer
- 再次调整视频转场逻辑
- 再次改造预加载架构

原因：

- 当前问题已经收敛为较小的视觉交接问题。
- 再扩大改动面，容易重新引入黑屏、旧 DOM 引用失效、A/B 错层等回归。
