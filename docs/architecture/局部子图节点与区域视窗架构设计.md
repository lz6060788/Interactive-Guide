# 局部子图节点与区域视窗架构设计

## 1. 文档目标

- 为当前基于总图局部区域的子节点体验设计一套新的运行时与数据契约。
- 降低“局部子图节点”对独立 HTML 页面和 iframe 的依赖，减少资源裁剪、重复加载与运行时开销。
- 保留当前业务中必须存在的两类能力：
  - 某些热点目标仍然是真正独立的 HTML 节点。
  - 某些边仍然需要视频转场，而不是内置 zoom。
- 为后续编辑器能力提供稳定的数据模型，包括区域标注、卡片创建定位、激活态预览和热点编辑。

## 2. 背景与问题

当前示例 `data/workspace/guide_1779344993154` 中，存在大量“看起来是 HTML 节点、实际是总图局部视窗”的子节点。

典型特征：

- 根节点 `root` 是一张总图原图。
- 从 `root` 到多个子节点通过 `zoom + focusQuad` 做无缝放大进入。
- 进入后的子节点仍然主要展示父图原图中的一部分区域。
- 同时在进入子节点后还会显示额外的信息卡片、标的信息和可点击路由动作。

当前实现的问题不在于 zoom 本身，而在于“局部视窗展示”和“进入后才出现的交互 overlay”被一起编码成了独立 HTML 节点：

- 为适配局部节点做了大量额外裁切和资源组织。
- 局部子图节点复用 iframe 渲染链路，带来不必要的加载、预加载和激活时序成本。
- 运行时节点语义不够准确，无法明确区分：
  - 普通图片节点
  - 基于父图原图的局部区域节点
  - 真正独立的 HTML 互动节点

## 3. 设计目标

### 3.1 必须达成

- 保留基于父图原图的无缝 zoomin 体验。
- 保留进入子节点后才显示的信息卡片、标的信息和动作按钮。
- 保留子节点继续挂载热点的能力。
- 支持在宽屏和窄屏下按不同视口比例求解初始显示窗口。
- 支持后续在编辑器中对局部区域和卡片进行可视化配置。

### 3.2 明确不做

- 第一阶段不追求把所有 HTML 节点都替换掉。
- 第一阶段不做完全通用的低代码卡片布局系统。
- 第一阶段不改动视频转场的基本链路，只补齐 region 节点参与转场时的目标窗口求解。

## 4. 核心结论

新的节点模型建议显式区分三类节点：

- `image`：普通图片节点。
- `region`：基于父图原图的局部子图节点。
- `html`：真正独立的 HTML 节点。

其中 `region` 节点的核心语义是：

- 主视觉仍来自 `sourceNodeId` 对应的父图原图。
- 节点只标注一个“滑动范围” `panRange`。
- 缩放后的初始显示窗口不是人工再画一个框，而是运行时根据：
  - `panRange` 的中心
  - `panRange` 的高度
  - 当前屏幕宽高比
  自动推导。
- 该节点进入后才显示自己的 overlay 和热点。

## 5. 数据契约设计

### 5.1 节点类型

建议在现有 `contentType` 的基础上新增更明确的 `nodeKind`。

```ts
type NodeKind = 'image' | 'region' | 'html'
type CoordSpace = 'source-normalized'
```

兼容策略：

- 老数据未声明 `nodeKind` 时：
  - `contentType === 'html'` 视为 `html`
  - 其他视为 `image`
- 新的 `region` 节点优先走 `nodeKind` 语义，不再依赖 `contentType: 'html'`

### 5.2 Region 节点视窗配置

```ts
interface NormalizedPoint {
  x: number
  y: number
}

interface QuadRange {
  topLeft: NormalizedPoint
  topRight: NormalizedPoint
  bottomRight: NormalizedPoint
  bottomLeft: NormalizedPoint
}

interface RegionInitialWindowRule {
  mode: 'derive-from-pan-range-center'
  fitBy: 'height'
}

interface RegionViewportConfig {
  sourceNodeId: string
  coordSpace: CoordSpace
  panRange: QuadRange
  initialWindowRule: RegionInitialWindowRule
}
```

说明：

- `panRange` 是编辑器唯一需要标注的区域。
- 坐标统一使用 `source-normalized`，即相对父图原图的归一化坐标。
- 初始窗口为派生数据，不单独存储。

### 5.3 Region 节点 overlay

当前示例项目中的进入后信息展示可先统一收敛到固定模板 `stock-info-v1`。

```ts
type RuntimeAction =
  | { type: 'navigate-edge'; edgeId: string }
  | { type: 'open-route'; route: string; openMode?: 'current-tab' | 'new-tab' }
  | { type: 'open-url'; url: string; target?: '_self' | '_blank' }

interface RegionOverlayStockItem {
  label: string
  valueText?: string
  action?: RuntimeAction
}

interface RegionOverlayCard {
  id: string
  title: string
  description?: string
  anchor: NormalizedPoint
  coordSpace: CoordSpace
  tags?: string[]
  stocks?: RegionOverlayStockItem[]
}

interface RegionOverlayConfig {
  template: 'stock-info-v1'
  showWhenActive: true
  cards: RegionOverlayCard[]
}
```

规则：

- `showWhenActive: true` 表示该 overlay 只在当前节点真正激活后显示。
- `anchor` 同样使用父图原图坐标系。
- `stocks[].action` 统一收敛为宿主层动作，不再依赖 HTML 节点私有脚本桥接。

## 6. Region 节点初始窗口求解规则

### 6.1 基本规则

运行时进入 `region` 节点后，不再依赖第二个手工框，而是按以下规则求解初始显示窗口：

1. 取 `panRange` 的中心点作为初始窗口中心。
2. 初始窗口高度取 `panRange.height`。
3. 根据当前视口宽高比计算初始窗口宽度：

```ts
initialWidth = panRangeHeight * viewportAspect
```

4. 如果 `initialWidth > panRangeWidth`，则将宽度截断为 `panRangeWidth`。
5. 最终初始窗口保持与 `panRange` 中心对齐。
6. 如果节点允许平移浏览，则平移边界不得超出 `panRange`。

### 6.2 含义

该规则实际表达了：

- 编辑器只负责标“可浏览的大区域”。
- 运行时根据屏幕形态推导“进入后第一眼看到的窗口”。
- 宽屏和窄屏差异不再通过单独标多个框解决，而由统一数学规则解算。

### 6.3 为什么按高度推宽度

这是当前体验中最稳定的做法，因为：

- 子图节点的视觉语义主要是“保持选中局部的纵向信息完整显示”。
- 宽度只是随终端分辨率变化的结果。
- 这样更容易在宽窄屏下保持核心视觉内容一致，而不需要为每种屏幕额外维护一套 landing 数据。

## 7. 边与转场设计

### 7.1 原则

- 边仍负责描述“如何从一个节点到另一个节点”。
- 节点负责描述“切换完成后的稳定态长什么样”。

### 7.2 Region 节点的 zoom

对于目标是 `region` 节点的 zoom，不建议继续把最终目标窗口写死成 manifest 中的 `focusQuad`，而建议在运行时动态求解。

可新增：

```ts
interface ZoomTransitionConfig {
  type: 'zoom'
  direction: 'in' | 'out'
  scale?: number
  centerX?: number
  centerY?: number
  focusMode?: 'center' | 'quad' | 'target-region-auto'
  focusQuad?: ZoomFocusQuad
  duration: number
  easing: EasingType
}
```

规则：

- 普通图片节点和 HTML 节点仍可继续使用 `center/quad`
- 目标为 `region` 节点时，优先使用 `target-region-auto`
- 真正的目标窗口由运行时根据 `panRange + 当前分辨率` 动态计算

### 7.3 视频转场

视频转场机制不需要被推翻：

- 某些边仍然可以通过 `videoUrl` 实现视频转场
- 视频结束后再切到 `region` 节点稳定态
- 稳定态仍按 `regionViewport` 规则渲染父图局部区域和 overlay

## 8. 运行时架构改造

### 8.1 总体原则

- 保留 `PlayerHost + PlayerCore + transitions/*` 的分层结构。
- 不推翻当前导航状态机和视频转场链路。
- 主要改造“节点稳定态渲染语义”。

### 8.2 PlayerHost 改造

当前宿主层主要分为：

- 图片节点渲染
- HTML 节点 iframe 渲染

建议扩成三种表面渲染：

- `renderImageNode()`
- `renderRegionNode()`
- `renderHtmlNode()`

其中 `renderRegionNode()` 负责：

- 获取 `regionViewport.sourceNodeId`
- 使用源节点原图作为基础表面
- 根据 `panRange + 当前容器尺寸` 求解初始窗口
- 应用固定视窗变换
- 在节点激活且不在转场中时渲染 overlay 与热点

### 8.3 PlayerCore 改造

建议新增：

- `getNodeKind(nodeId)`
- `isRegionNode(nodeId)`
- `resolveRegionViewport(nodeId, viewportSize)`

核心变化：

- `resolveForwardTransition()` 需要识别目标是否为 `region` 节点
- 当边配置 `zoom + target-region-auto` 时，调用运行时窗口求解逻辑
- `switchNode()` 本身仍只更新状态，不直接承担视窗和 overlay 细节

### 8.4 zoom renderer 改造

当前 zoom renderer 主要消费 `focusQuad / center`。

建议新增一条运行时注入路径：

```ts
interface TransitionContext {
  runtimeFocusFrame?: {
    scale: number
    translateX: number
    translateY: number
  }
}
```

规则：

- 普通节点继续走现有 `focusQuad / center`
- `region` 节点的 `target-region-auto` 由宿主或 core 先求出目标 focus frame
- zoom renderer 只负责消费解算结果，不直接理解 region 业务

### 8.5 region viewport 求解模块

建议新增独立模块，例如：

- `src/runtime/player-core/region-viewport.ts`

负责：

- `resolveInitialRegionWindow()`
- `clampRegionPanOffset()`
- `buildRegionImageTransform()`

这样可以把当前图片 `fitHeight / fitWidth` 与 region 节点的局部视窗求解逻辑统一到一个可测试模块中。

## 9. overlay 与动作协议

### 9.1 overlay 显示时机

region 节点的 overlay 必须遵守：

- 只有在当前节点真正成为稳定态后显示
- 转场中不得提前显示
- 返回父节点或切换到其他节点后立即隐藏

### 9.2 动作执行

建议由宿主层统一执行动作：

```ts
private executeRuntimeAction(action: RuntimeAction): void
```

当前第一阶段只需支持：

- `navigate-edge`
- `open-route`
- `open-url`

这样可以：

- 让 region 节点不再依赖 iframe bridge
- 让信息卡片与热点行为统一进入同一动作协议
- 为后续 HTML overlay 或其他宿主动作扩展留出一致入口

## 10. 编辑器设计

### 10.1 编辑目标

第一阶段编辑器不做通用页面搭建器，而是只服务 `region` 节点的三个核心能力：

- 标注 `panRange`
- 创建并定位进入后才显示的卡片
- 配置该节点激活态下的热点

### 10.2 操作流

1. 从父节点创建子节点，选择类型为 `region`
2. 在父图上框选一次 `panRange`
3. 切换到“激活态预览”
4. 在激活态中新增卡片
5. 拖拽卡片锚点位置
6. 编辑卡片标题、描述、tags、标的信息和动作
7. 在激活态中新增该节点热点
8. 切换不同分辨率预览，验证初始窗口、卡片和热点位置

### 10.3 两种预览态

虽然编辑器不需要两个框，但仍建议保留两种预览态：

- `源图标注态`
  - 用于标 `panRange`
  - 用于确认该 region 节点在父图中的来源
- `激活态预览`
  - 用于展示运行时实际求解出的初始窗口
  - 用于显示该节点激活后才出现的 overlay 与热点

### 10.4 分辨率预览

由于初始窗口宽度依赖当前宽高比，编辑器必须支持切换不同分辨率预览，例如：

- 手机竖屏
- 平板横屏
- 宽屏容器

运营在编辑时应看到：

- 同一个 `panRange` 在不同屏幕比下推导出的初始窗口差异
- 卡片与热点在不同宽高比下是否仍保持合理视觉落点

## 11. 迁移策略

### 11.1 先迁“查看器壳”节点

适合优先迁成 `region` 节点的，是当前那些“HTML 文件只是在展示一张局部图 + 少量标签/卡片”的节点，例如：

- `ground-station`
- `launch-detection`
- `rocket-fuel`
- `monitoring-and-operations`
- `satellite-communication`
- `rocket-testing`
- `node_1779440240699`

迁移方式：

- 旧 HTML 页中的局部区域定义 -> `regionViewport.panRange`
- 旧 HTML 页中的卡片与标的信息 -> `regionOverlay.cards`
- 旧 HTML 页中的点击路由 -> `RuntimeAction`
- 旧 HTML 页中的子热点 -> 节点自己的 `hotspots`

### 11.2 保留真正复杂的 HTML 节点

例如 `rocket.html` 这类包含完整 three.js 场景和复杂交互状态机的节点，应继续保留为 `html` 节点。

### 11.3 分阶段实施

建议顺序：

1. 增加共享类型，兼容旧数据
2. 运行时支持 `region` 节点稳定态渲染
3. 为 zoom 增加 `target-region-auto`
4. 实现 `stock-info-v1` 固定模板 overlay
5. 选择一个示例节点完成端到端迁移验证
6. 再补编辑器里的 region 标注与卡片编辑

## 12. 风险与注意事项

### 12.1 主要风险

- 老数据大量依赖 `contentType: html`，迁移时需要明确识别“真 html”和“假 html”
- region 节点的窗口求解若与当前 zoom 逻辑耦合不清，容易出现落点不一致
- 宽窄屏差异全部交给运行时推导后，需要确保编辑器预览与正式运行时完全一致

### 12.2 控制原则

- 统一坐标系：region、卡片、热点全部优先使用父图原图坐标
- overlay 只在节点激活后显示，不提前渲染
- 转场实现层只消费 focus frame，不直接写 region 业务判断
- 复杂 HTML 节点继续保留，不做强制迁移

## 13. 当前结论

当前推荐的稳定方向是：

- 用 `region` 节点承接“父图原图局部视窗 + 激活后 overlay”这一类节点
- 用统一的 `panRange` 和“按高度推宽度”的规则求解初始窗口
- 用宿主层 overlay 替代大部分当前的查看器壳 HTML
- 保留 `html` 节点承接真正复杂的独立互动页
- 保留边的视频转场和普通 zoom 能力，只对 region 节点增加动态目标窗口求解

这样既能保留当前最有价值的无缝 zoom 体验，也能把运行时语义和性能成本重新拉回可控范围。
