# Interactive Guide 构建任务流与目录结构设计

## 1. 文档目标

- 这份文档用于把 `Interactive Guide` 的构建侧方案落成可实施的任务模型和目录结构。
- 它重点回答四个问题：
  1. 构建任务应该分成哪些阶段。
  2. 每个阶段产出什么中间结果。
  3. 文件和资源应该如何落盘。
  4. 管理端如何查看、重试和恢复构建状态。

## 2. 设计原则

- 构建系统是“离线知识编译器”，不是运行时服务的镜像。
- 一次构建必须允许断点续跑，不能因为某个节点失败就整包报废。
- 节点图片、热点标注、边视频三类任务应能独立重试。
- 中间结果要可审计、可回看、可被管理端直接读取。
- 第一阶段优先本地文件系统落盘，不急于引入数据库。

## 3. 构建任务的总体层级

```text
PackageBuild
-> ValidatePackageStage
-> PrepareBuildStage
-> BuildNodesStage
-> BuildHotspotsStage
-> BuildEdgesStage
-> PublishStage
```

- `PackageBuild` 是一次完整的包级构建。
- 包级构建下再拆节点、热点、边三个资源子阶段。
- 这些阶段既要能串行推进，也要允许针对局部对象单独重跑。

## 4. 构建阶段设计

### 4.1 Stage 1: ValidatePackage

- 目标：
  - 校验 `KnowledgePackage` 结构合法
  - 校验节点和边的引用关系
  - 校验根节点、分辨率、hotspot 关联信息
- 输入：
  - 当前知识包 JSON
- 输出：
  - `validation-report.json`
  - 是否允许进入下一阶段

- 失败策略：
  - 校验失败直接终止整包构建
  - 但保留报告供管理端展示

### 4.2 Stage 2: PrepareBuild

- 目标：
  - 为本次构建生成唯一 `buildId`
  - 冻结本次输入快照
  - 初始化目录、状态文件和空任务记录
- 输入：
  - 已通过校验的知识包
- 输出：
  - `input/package.snapshot.json`
  - `build.json`
  - 节点、边、热点的初始记录

### 4.3 Stage 3: BuildNodes

- 目标：
  - 为每个节点生成页面编排结果
  - 为每个节点生成主图
- 输入：
  - 知识包节点
  - 包级风格配置
  - 节点 `keyContent / presentationIntent / hotspots.label`
- 输出：
  - `nodes/{nodeId}/planner.json`
  - `nodes/{nodeId}/image.png`
  - `nodes/{nodeId}/node-record.json`

- 节点子任务建议再拆成两步：

```text
NodeBuildTask
-> plan-node
-> render-node-image
```

- 这样做的原因：
  - 页面编排失败和图片生成失败是两种问题
  - 后续单节点重试时能更精确定位失败点

### 4.4 Stage 4: BuildHotspots

- 目标：
  - 基于已生成节点图片和 `hotspots.label` 推荐热点坐标
  - 生成初始热点结果，供后续人工校准
- 输入：
  - 当前节点图片
  - 当前节点的 `hotspots`
  - 当前包的分辨率
- 输出：
  - `nodes/{nodeId}/hotspots.recommended.json`
  - `nodes/{nodeId}/hotspots.final.json`

- 第一阶段建议：
  - 若没有自动推荐能力，可先直接生成空壳 `recommended` 文件
  - 由管理端热点校准弹窗补齐 `final` 文件

### 4.5 Stage 5: BuildEdges

- 目标：
  - 为每条边生成转场 prompt
  - 为每条边生成转场视频
- 输入：
  - 起点节点图片
  - 终点节点图片
  - 边关系文案
  - 包级 `transitionStyle`
- 输出：
  - `edges/{edgeId}/transition.json`
  - `edges/{edgeId}/transition.mp4`
  - `edges/{edgeId}/edge-record.json`

### 4.6 Stage 6: Publish

- 目标：
  - 汇总节点、边、热点最终结果
  - 生成前端消费用的 `manifest.json`
  - 产出发布目录
- 输入：
  - 各阶段最终成功结果
- 输出：
  - `publish/manifest.json`
  - `publish/assets/...`
  - `publish/summary.json`

## 5. 包级任务与子任务模型

### 5.1 PackageBuildRecord

```ts
interface PackageBuildRecord {
  buildId: string
  packageId: string
  packageVersion: string
  status: 'pending' | 'running' | 'partial_failed' | 'success' | 'failed'
  currentStage:
    | 'validate'
    | 'prepare'
    | 'build_nodes'
    | 'build_hotspots'
    | 'build_edges'
    | 'publish'
    | 'done'
  createdAt: string
  updatedAt: string
  startedAt?: string
  finishedAt?: string
  summary: {
    nodeTotal: number
    nodeSuccess: number
    hotspotTotal: number
    hotspotReady: number
    edgeTotal: number
    edgeSuccess: number
  }
}
```

### 5.2 NodeBuildRecord

```ts
interface NodeBuildRecord {
  buildId: string
  nodeId: string
  status: 'pending' | 'running' | 'success' | 'failed'
  plannerStatus: 'pending' | 'running' | 'success' | 'failed'
  imageStatus: 'pending' | 'running' | 'success' | 'failed'
  plannerOutputPath?: string
  imagePath?: string
  errorMessage?: string
  updatedAt: string
}
```

### 5.3 HotspotBuildRecord

```ts
interface HotspotBuildRecord {
  buildId: string
  nodeId: string
  status: 'pending' | 'running' | 'success' | 'failed'
  recommendationStatus: 'pending' | 'running' | 'success' | 'failed'
  manualAdjusted: boolean
  recommendedPath?: string
  finalPath?: string
  errorMessage?: string
  updatedAt: string
}
```

### 5.4 EdgeBuildRecord

```ts
interface EdgeBuildRecord {
  buildId: string
  edgeId: string
  status: 'pending' | 'running' | 'success' | 'failed'
  promptStatus: 'pending' | 'running' | 'success' | 'failed'
  videoStatus: 'pending' | 'running' | 'success' | 'failed'
  transitionPath?: string
  videoPath?: string
  errorMessage?: string
  updatedAt: string
}
```

## 6. 目录结构设计

### 6.1 顶层目录建议

```text
Interactive-Guide/
├─ data/
│  ├─ packages/
│  ├─ builds/
│  └─ publish/
├─ docs/
└─ src/
```

- `data/packages/`
  - 放知识包原始输入或当前编辑后的包内容
- `data/builds/`
  - 放每次构建的中间结果和状态
- `data/publish/`
  - 放最终对外发布版本

### 6.2 package 目录建议

```text
data/packages/{packageId}/
├─ current/
│  └─ package.json
└─ history/
   └─ {timestamp}.json
```

- `current/package.json`
  - 当前管理端正在编辑的最新版本
- `history/`
  - 保存历史快照，便于回滚和对比

### 6.3 build 目录建议

```text
data/builds/{buildId}/
├─ build.json
├─ validation-report.json
├─ input/
│  └─ package.snapshot.json
├─ nodes/
│  └─ {nodeId}/
│     ├─ planner.json
│     ├─ image.png
│     ├─ node-record.json
│     ├─ hotspots.recommended.json
│     └─ hotspots.final.json
├─ edges/
│  └─ {edgeId}/
│     ├─ transition.json
│     ├─ transition.mp4
│     └─ edge-record.json
└─ logs/
   ├─ build.log
   └─ events.jsonl
```

### 6.4 publish 目录建议

```text
data/publish/{packageId}/{version}/
├─ manifest.json
├─ summary.json
└─ assets/
   ├─ nodes/
   │  └─ {nodeId}.png
   └─ edges/
      └─ {edgeId}.mp4
```

- 发布目录应尽量简单，避免把构建中间文件暴露给运行时。
- 运行时只依赖 `manifest.json` 和 `assets/`。

## 7. 构建状态流转

### 7.1 包级状态

```text
pending
-> running
-> success
```

- 若某些节点或边失败，但仍然产出部分可用结果，包级可进入：

```text
running
-> partial_failed
```

- 若校验失败或关键阶段完全失败，则进入：

```text
running
-> failed
```

### 7.2 节点与边状态

```text
pending
-> running
-> success | failed
```

- 节点和边都应支持从 `failed` 再次进入 `running`。
- 这意味着系统不能把失败任务视为不可变对象。

## 8. 重试与断点续跑策略

### 8.1 为什么必须支持断点续跑

- 新项目的资源生成成本高，尤其是图片和视频。
- 如果整包一旦中断就必须从头跑，运营体验会很差。
- 因此构建系统需要能识别：
  - 哪些节点已经成功
  - 哪些热点已经人工校准
  - 哪些边只差视频没生成

### 8.2 第一阶段重试粒度

- 支持以下粒度：
  - 整包重构建
  - 单节点重构建
  - 单节点热点重推荐
  - 单边重构建

### 8.3 断点恢复规则

- 若 `node-record.json` 显示节点图片已成功，默认跳过该节点图片重建。
- 若 `hotspots.final.json` 已存在且 `manualAdjusted = true`，默认跳过热点重推荐。
- 若 `edge-record.json` 显示视频已成功，默认跳过该边视频重建。
- 用户主动点“重跑”时，再显式覆盖已有结果。

## 9. 缓存策略建议

### 9.1 第一阶段缓存目标

- 避免同一节点内容重复触发页面编排
- 避免同一图片 prompt 重复生成图片
- 避免同一起止页组合重复生成视频

### 9.2 缓存键思路

```text
node planner cache key
= packageId + nodeId + node content hash + style hash

node image cache key
= imagePrompt + resolution + visualStyle

edge video cache key
= fromImageHash + toImageHash + relationLabel + transitionStyle
```

- 第一阶段缓存文件可以先和构建目录并存。
- 后续如果需要跨 build 复用，再抽成独立缓存目录。

## 10. 管理端如何消费构建状态

### 10.1 总览页关注什么

- 包级最新构建状态
- 最近一次构建时间
- 是否可导出
- 是否已有可预览版本

### 10.2 工作台关注什么

- 节点图片状态
- 边视频状态
- 热点是否待校准
- 是否存在失败对象

### 10.3 推荐接口返回

```ts
interface BuildSummaryPayload {
  buildId: string
  status: 'pending' | 'running' | 'partial_failed' | 'success' | 'failed'
  currentStage: string
  nodeSummary: {
    total: number
    success: number
    failed: number
  }
  hotspotSummary: {
    total: number
    ready: number
    pending: number
  }
  edgeSummary: {
    total: number
    success: number
    failed: number
  }
}
```

## 11. 发布阶段的收口原则

### 11.1 发布不应直接引用构建目录

- 构建目录是中间产物，包含日志、快照和失败记录。
- 发布目录应只保留前端真正需要的结果。
- 这样运行时更干净，也便于做静态部署。

### 11.2 发布前检查

- 至少应检查：
  - 根节点图片存在
  - 所有已启用边的视频存在或允许为空
  - 所有热点都有 `normalizedX / normalizedY`
  - `manifest.json` 能完整串起节点和边

## 12. 与后续实现的连接点

### 12.1 对管理端的意义

- 管理端的“发起构建”按钮，对应创建 `PackageBuildRecord`
- 管理端的节点、边状态，来自各自的 build record
- 管理端的热点校准弹窗，最终写回 `hotspots.final.json` 和知识包当前状态

### 12.2 对运行时的意义

- 运行时不需要知道构建过程
- 运行时只需要：
  - `manifest.json`
  - 节点图片
  - 边视频

### 12.3 对后续服务端实现的意义

- 后端即使第一阶段不用数据库，也可以先围绕这些文件契约实现
- 如果后面接入数据库，也只是把当前文件记录映射到持久化层，不必推翻任务模型

## 13. 第一阶段实现建议

### 13.1 建议先做的最小闭环

1. 读取 `package.json`
2. 生成 `buildId`
3. 写入 `build.json`
4. 跑校验
5. 跑节点编排与图片生成
6. 生成人工可编辑的热点文件
7. 跑边视频生成
8. 输出 `publish/manifest.json`

### 13.2 建议稍后再做的能力

- 并发队列
- 分布式任务调度
- 数据库存档
- 多版本灰度发布
- 复杂缓存淘汰

## 14. 最终建议

- 第一阶段先把构建系统做成“文件系统驱动的可恢复任务流”。
- 任务记录、中间结果、最终产物三者要清晰分层，不要混在一起。
- 只要 `build record + build directory + publish directory` 这三层稳定下来，后续不论补 UI、补接口还是补数据库，整体结构都不会乱。
