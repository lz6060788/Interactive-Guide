# 生图内容描述规范

## 1. 文档目标

这份规范用于指导如何把原始内容转换为用于图片生成和信息图表达的描述信息。

当前项目存在两类明显不同的任务：

- `scene-mode`：偏视觉导览，目标是生成具有场景感和氛围感的画面。
- `infographic-mode`：偏知识导览，目标是生成以内容理解为主、图文并茂的信息图。

两类任务不能共用同一套描述策略。

## 2. 总原则

### 2.1 先判断模式，再写描述

- 如果任务重点是氛围、场景、视觉冲击，使用 `scene-mode`。
- 如果任务重点是解释概念、梳理关系、帮助理解，使用 `infographic-mode`。
- `新闻播报`、`常识介绍`、`内容解读`、`知识导览` 默认优先使用 `infographic-mode`。

### 2.2 先决定讲什么，再决定怎么画

- 图片描述不能替代原始内容。
- 对知识型页面，必须先提炼内容主旨、关键点、原文依据，再补视觉表达。
- 视觉元素服务于知识表达，不能反过来吞掉知识内容。

### 2.3 `keyContent` 不再承担全部职责

当前实践中，节点内容建议至少拆为：

- `summary`：这页在讲什么
- `keyPoints`：必须保留的 3-5 个知识点
- `sourceText`：原文参考
- `visualIntent`：适合怎样的图示表达
- `keyContent`：兼容旧链路的补充视觉描述

其中：

- `summary / keyPoints / sourceText` 属于内容层
- `visualIntent / keyContent` 属于视觉层

## 3. Scene Mode

### 3.1 适用场景

- 需要突出场景氛围和视觉主体的导览页
- 偏插画化的概念展示
- 主题海报、封面页、场景总览页

### 3.2 写法原则

- 用具象、可见的物体描述画面
- 用一个核心锚点串联其他元素
- 用视角、主体、节奏制造节点差异
- 少写抽象结论，多写能被画出来的对象和关系

### 3.3 不要做什么

#### 不要直接规定布局拆分

```text
错误：画面从上到下分为三个纵向色块区域
错误：以三张竖向卡片展示
错误：左右两栏并排
```

在 `scene-mode` 中，布局应主要交给风格模板和模型决定。

#### 不要把多个知识点写成僵硬编号

```text
错误：
三大环节：
1. 上游制造
2. 中游发射
3. 下游应用
```

这会让模型更容易生成机械分段卡片，而不是自然场景。

#### 不要让多个节点复用同一视觉主体

```text
错误：root 和 downstream 都以“画面中央是一枚巨大的火箭”开头
```

不同节点必须具备明显不同的视觉主体和视角。

### 3.4 示例

以商业航天产业链为例：

```text
root: 鸟瞰视角，多枚火箭、卫星星座、发射场和地面设施共同构成开阔全景
upstream: 实验室工作台俯视，材料样品、芯片元件和检测工具散落
midstream: 火箭升空瞬间，尾焰、发射台、跟踪天线和地面终端形成动态链条
downstream: 卫星向地球广播信号，覆盖区内散落终端设备和应用场景
```

## 4. Infographic Mode

### 4.1 适用场景

- `新闻播报`
- `常识介绍`
- `内容解读`
- `课程导览`
- `知识图谱`
- `概念说明`
- `机制分析`

### 4.2 核心目标

让用户更容易理解原始内容，而不是只获得一张“相关插画”。

因此在 `infographic-mode` 中：

- 内容保真优先于视觉隐喻
- 信息密度优先于纯留白美感
- 模块关系优先于单一主场景
- 原生文本区、图示区、关系区可以共存

### 4.3 写法原则

#### 先提炼内容骨架

至少明确以下内容：

- 这页主题是什么
- 哪 3-5 个点绝对不能丢
- 是否存在定义、公式、对比、流程、因果、结论
- 适合什么页面骨架

#### 允许描述信息结构

在 `infographic-mode` 中，可以写：

- 对比关系
- 上下游关系
- 因果链
- 时间线
- 模块区
- 解释区与示意图区的并列关系

但应避免写死像素级布局。

```text
正确：以纵向阅读的信息图组织内容，上部给出主题和核心结论，中部呈现两组对比关系，下部给出应用或延伸
错误：标题高度固定为 80px，下面分 3 个 120px 卡片
```

#### 允许保留可读信息

在知识导览里，以下内容不应被强制剔除：

- 术语
- 公式
- 关键标签
- 对比项名称
- 机制名称
- 结论性短句

错误做法不是“出现文字”，而是“整页只剩大段文字，没有图示支撑”。

#### 视觉表达要服务于解释

优先使用：

- 对比图
- 流程图
- 关系图
- 坐标/曲线示意
- 模块卡片
- 数据标签

谨慎使用：

- 过强的文学化场景
- 与主题弱相关的装饰物
- 只强调氛围、不表达关系的背景插画

### 4.4 不要做什么

#### 不要把原文改写成纯视觉隐喻

```text
错误：用一枚巨大的蛋糕和天平替代 GDP 核算全部内容
```

如果原文重点是核算方法、公式与差异，只留下蛋糕意象就会丢失知识主体。

#### 不要只给出一个大场景

```text
错误：整页只有一个经济驾驶舱场景，所有知识点都被埋在装饰里
```

信息图页面应有明确的信息承载区域，而不是只靠用户猜测寓意。

#### 不要让空白压过信息

特别是在移动端竖屏中，应避免：

- 中间一块横向展板
- 顶部超大标题
- 上下大面积留白
- 只有一处信息主体，其他区域只是背景

### 4.5 推荐页面骨架

#### `news-report`

- 顶部：事件主题与时间地点
- 中部：事件进展、关键人物、影响范围
- 下部：数据、地图、时间线或延伸阅读

#### `common-knowledge`

- 顶部：核心定义或主题句
- 中部：机制图、关系图或概念对比
- 下部：例子、应用、延伸问题

#### `content-analysis`

- 顶部：观点或结论
- 中部：依据、逻辑链、关键争议点
- 下部：影响、风险、后续观察点

### 4.6 示例

以“GDP 核算的三种方法”为例：

```text
正确：以教材式信息图呈现 GDP 的三种核算路径。顶部给出主题和结论：生产法、收入法、支出法理论上应得到一致结果。中部用三个相邻模块分别解释三种方法，每个模块保留对应公式和代表性要素。下部补充三者适用角度与统计理解。整体是竖屏高信息密度页面，少量仪器或账本元素作为辅助，不要用单一实验室场景覆盖全部信息。
```

## 5. 移动端竖屏附加规则

适用于 `infographic-mode`，必要时也可用于 `scene-mode`：

- 明确要求从上到下阅读
- 顶部、中部、下部都应有有效内容区
- 画面有效内容占比应明显高于留白
- 避免把横向海报或展板塞进竖屏画布
- 标题区保持克制，不要吞掉大量高度
- 优先组织为 `3-5` 个纵向串联的信息模块

## 6. 模式选择建议

| 任务类型 | 推荐模式 | 说明 |
| --- | --- | --- |
| 封面页 / 场景导览 | `scene-mode` | 强调氛围、主体、视觉记忆点 |
| 新闻播报 | `infographic-mode` | 强调事实、时间、影响、结构 |
| 常识介绍 | `infographic-mode` | 强调定义、原理、分类、例子 |
| 内容解读 | `infographic-mode` | 强调观点、依据、争议、结论 |
| 学科导览 | `infographic-mode` | 强调关系、机制、层级、知识点 |

## 7. 最终检查清单

在提交描述前，至少检查以下问题：

- 这是 `scene-mode` 还是 `infographic-mode`
- 页面最重要的是“场景感”还是“解释力”
- 原文最关键的知识点是否被保留
- 是否出现了过强的装饰性隐喻
- 是否适配移动端竖屏阅读
- 是否避免了多个节点长得像同一张图的变体
