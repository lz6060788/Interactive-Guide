# Interactive Guide 管理端工作台组件拆分与状态设计

## 1. 文档目标

- 这份文档用于把现有管理端方案进一步落到可实现的前端结构。
- 核心目标不是补充新的产品需求，而是回答三个实现问题：
  1. 页面应该拆成哪些组件。
  2. 状态应该放在哪一层管理。
  3. 弹窗、抽屉、画布和热点拖拽之间如何协作。

## 2. 实现范围

- 第一阶段只覆盖管理端中的两个页面：
  - `知识包总览页`
  - `知识编排工作台`
- 以下能力作为工作台内的浮层能力处理：
  - `预览弹窗`
  - `热点校准弹窗`
  - `详情抽屉`

## 3. 页面与组件总览

```text
App
-> PackageListPage
-> WorkbenchPage
   -> WorkbenchToolbar
   -> WorkbenchSidebar
   -> KnowledgeFlowCanvas
   -> DetailDrawer
   -> PreviewModal
   -> HotspotEditorModal
```

- 总览页负责包级操作。
- 工作台负责节点、边、资源状态与人工干预。
- 预览和热点校准都挂在工作台下，不单独拆路由。

## 4. 知识包总览页组件拆分

### 4.1 建议组件

```text
PackageListPage
-> PackageListToolbar
-> PackageListFilters
-> PackageListTable
-> PackageRowActions
```

### 4.2 组件职责

- `PackageListPage`
  - 拉取列表数据
  - 承接导入、导出、删除、新建等包级动作
- `PackageListToolbar`
  - 放 `导入 JSON / 新建知识包 / 批量导出`
- `PackageListFilters`
  - 放状态筛选、关键词筛选、更新时间排序
- `PackageListTable`
  - 渲染包列表
  - 透出行选中与行操作事件
- `PackageRowActions`
  - 放 `进入工作台 / 发起构建 / 预览 / 导出 / 删除`

### 4.3 总览页状态建议

```ts
interface PackageListPageState {
  keyword: string
  statusFilter: 'all' | 'idle' | 'running' | 'success' | 'failed'
  selectedPackageIds: string[]
  exportingPackageIds: string[]
  deletingPackageIds: string[]
}
```

- 总览页状态以局部页面状态为主。
- 不建议一开始就把列表筛选状态放进全局 store。
- 只有当后续出现跨页共享需求时，再把筛选条件上提。

## 5. 工作台页面组件拆分

### 5.1 总体结构

```text
WorkbenchPage
-> WorkbenchToolbar
-> WorkbenchSidebar
-> KnowledgeFlowCanvas
-> DetailDrawer
-> PreviewModal
-> HotspotEditorModal
```

### 5.2 组件职责

- `WorkbenchPage`
  - 拉取单个知识包详情
  - 组织画布、抽屉、弹窗所需状态
  - 协调保存、构建、发布等顶层动作
- `WorkbenchToolbar`
  - 放 `保存 / 校验 / 发起构建 / 打开预览 / 发布`
- `WorkbenchSidebar`
  - 显示节点与边快速列表
  - 支持筛选失败项和未生成项
- `KnowledgeFlowCanvas`
  - 包装 `React Flow`
  - 渲染节点、边、连线状态和选中态
- `DetailDrawer`
  - 根据当前选中对象切换内容
  - 支持知识包、节点、边三种编辑模式
- `PreviewModal`
  - 承接运行时体验预览
- `HotspotEditorModal`
  - 承接当前节点主图上的 hotspot 校准

## 6. 工作台中的子组件建议

### 6.1 Toolbar 组件

```text
WorkbenchToolbar
-> SaveButton
-> ValidateButton
-> BuildButton
-> PreviewButton
-> PublishButton
```

- 工具栏只负责触发动作，不持有业务数据。
- 按钮是否禁用由上层状态驱动，例如：
  - 正在保存时禁用 `保存`
  - 包内存在未修复错误时禁用 `发布`

### 6.2 Sidebar 组件

```text
WorkbenchSidebar
-> SidebarFilterTabs
-> NodeQuickList
-> EdgeQuickList
-> BuildStatusSummary
```

- `NodeQuickList` 负责节点快速跳转与失败定位。
- `EdgeQuickList` 负责边快速跳转与失败定位。
- `BuildStatusSummary` 用于显示：
  - 节点图片成功数
  - 边视频成功数
  - 热点待校准数

### 6.3 Canvas 组件

```text
KnowledgeFlowCanvas
-> FlowNodeRenderer
-> FlowEdgeRenderer
-> CanvasStatusLegend
```

- `FlowNodeRenderer`
  - 展示标题、图片状态、热点数量
- `FlowEdgeRenderer`
  - 展示关系文案、视频状态
- `CanvasStatusLegend`
  - 展示颜色、角标、失败态说明

## 7. 抽屉与弹窗组件设计

### 7.1 DetailDrawer

```text
DetailDrawer
-> PackageForm
-> NodeForm
-> EdgeForm
```

- `PackageForm`
  - 编辑包级配置，如分辨率、画面风格、转场风格
- `NodeForm`
  - 编辑 `title / keyContent / presentationIntent / hotspots`
  - 支持触发 `重跑节点图片`
- `EdgeForm`
  - 编辑 `relationLabel`
  - 支持触发 `重跑边视频`

### 7.2 PreviewModal

```text
PreviewModal
-> RuntimePreviewPlayer
-> PreviewHeader
-> PreviewFooter
```

- `RuntimePreviewPlayer` 尽量贴近真实用户端播放器。
- 弹窗只做验证，不承担编辑职责。

### 7.3 HotspotEditorModal

```text
HotspotEditorModal
-> HotspotEditorHeader
-> HotspotImageStage
-> HotspotListPanel
```

- `HotspotEditorHeader`
  - 放 `保存 / 重新推荐 / 关闭`
- `HotspotImageStage`
  - 显示主图
  - 叠加多个白点热点
  - 处理拖拽、选中和位置换算
- `HotspotListPanel`
  - 展示当前节点下所有热点
  - 支持切换当前选中热点

## 8. 推荐状态分层

### 8.1 为什么要分层

- 如果所有状态都堆在一个 store 里，工作台会很快失控。
- 更合理的做法是分成三层：
  1. 服务端实体状态
  2. 页面 UI 状态
  3. 短生命周期交互状态

### 8.2 服务端实体状态

```ts
interface WorkbenchEntityState {
  packageDetail: KnowledgePackage | null
  nodesById: Record<string, KnowledgeNode>
  edgesById: Record<string, KnowledgeEdge>
}
```

- 这一层是业务真值来源。
- 所有保存、构建、导出、发布都基于这层数据。

### 8.3 页面 UI 状态

```ts
interface WorkbenchUiState {
  selectedType: 'package' | 'node' | 'edge' | null
  selectedId: string | null
  drawerOpen: boolean
  previewOpen: boolean
  hotspotModalOpen: boolean
  hotspotEditingNodeId: string | null
  sidebarFilter: 'all' | 'failed' | 'missing-resource'
}
```

- 这一层只决定界面呈现，不承载业务真值。

### 8.4 短生命周期交互状态

```ts
interface TransientInteractionState {
  saving: boolean
  validating: boolean
  building: boolean
  publishing: boolean
  draggingHotspotId: string | null
  activeHotspotId: string | null
}
```

- 这一层主要服务按钮禁用、加载态和拖拽态。
- 不建议把拖拽中的临时坐标直接写回远端对象。
- 应先写入本地编辑态，确认保存后再提交。

## 9. 事件流设计

### 9.1 选中节点或边

```text
点击画布对象
-> 更新 selectedType / selectedId
-> 打开 DetailDrawer
-> 渲染对应表单
```

### 9.2 编辑节点信息

```text
在 NodeForm 修改字段
-> 更新本地表单草稿
-> 点击保存
-> 调用 node 更新接口
-> 成功后回写 entity state
```

### 9.3 打开预览弹窗

```text
点击打开预览
-> previewOpen = true
-> 加载当前 package 的预览数据
-> 在 RuntimePreviewPlayer 中运行
```

### 9.4 打开热点校准弹窗

```text
点击打开热点校准
-> hotspotModalOpen = true
-> hotspotEditingNodeId = 当前节点 id
-> 读取节点图片与 hotspots
-> 在 HotspotImageStage 中渲染
```

### 9.5 拖拽热点

```text
按下 hotspot
-> 记录 activeHotspotId
-> 拖拽中根据容器尺寸换算坐标
-> 更新本地 draftHotspots
-> 点击保存后批量提交
```

## 10. 热点校准弹窗的状态建议

### 10.1 推荐结构

```ts
interface HotspotEditorState {
  nodeId: string
  imageUrl: string
  containerWidth: number
  containerHeight: number
  activeHotspotId: string | null
  draftHotspots: Array<{
    edgeId: string
    targetNodeId: string
    label: string
    normalizedX: number
    normalizedY: number
    radius?: number
    status?: 'idle' | 'running' | 'success' | 'failed'
  }>
}
```

### 10.2 为什么优先保存归一化坐标

- 弹窗里的图片显示尺寸是可变的。
- 如果只保存像素坐标，容器一变化热点就会漂移。
- 因此建议：
  - 渲染时从 `normalizedX / normalizedY` 计算像素位置
  - 拖拽时再从像素位置反算归一化坐标

### 10.3 坐标换算

```ts
function toPixelPosition(
  normalizedX: number,
  normalizedY: number,
  width: number,
  height: number,
) {
  return {
    x: normalizedX * width,
    y: normalizedY * height,
  }
}

function toNormalizedPosition(x: number, y: number, width: number, height: number) {
  return {
    normalizedX: width === 0 ? 0 : x / width,
    normalizedY: height === 0 ? 0 : y / height,
  }
}
```

## 12. 第一阶段实现顺序

### 12.1 最小可行顺序

1. 先实现 `知识包总览页`
2. 再实现 `WorkbenchPage` 基础框架
3. 接入 `React Flow` 节点与边渲染
4. 接入 `DetailDrawer`
5. 接入 `PreviewModal`
6. 接入 `HotspotEditorModal`
7. 最后补保存、构建、发布等动作

### 12.2 为什么这样排

- 因为画布、抽屉、弹窗的协作关系先跑通，后面再接真实接口成本更低。
- 如果一开始就先接复杂接口，很容易把 UI 结构绑死在临时数据流上。

## 13. 最终建议

- 第一阶段工作台最好坚持“页面少、浮层清晰、状态分层”的原则。
- `React Flow` 只负责图编排和对象选中，不要把表单编辑逻辑塞进节点内部。
- `DetailDrawer` 负责常规编辑，`PreviewModal` 负责体验验证，`HotspotEditorModal` 负责精细校准。
- 这样拆分后，后续无论你接真实接口、补 Zustand/Redux，还是加任务轮询，都不会推翻现有结构。
